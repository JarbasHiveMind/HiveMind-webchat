# AGENTS.md — `HiveMind-webchat`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

A browser-based WebChat satellite for [HiveMind](https://github.com/JarbasHiveMind).
The Python side (`hivemind_webchat/`) is a Tornado static web server; the actual
HiveMind connection runs in the browser via the [HiveMind-js](https://github.com/JarbasHiveMind/HiveMind-js)
client. There is also an optional headless bridge (`WebchatBridge`) that speaks
the HiveMind protocol directly from Python without a browser. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running [OpenVoiceOS](https://github.com/OpenVoiceOS).
The hub is [HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core).
Sibling repos: the client library [HiveMind-js](https://github.com/JarbasHiveMind/HiveMind-js),
the transport [hivemind-bus-client](https://github.com/JarbasHiveMind/HiveMind-bus-client).

## Layout / build / test

This is a Python + JavaScript hybrid with two independent test suites.

- Package module: `hivemind_webchat/`. Python tests live in `tests/` (with the
  e2e suite under `tests/e2e/`) — the single test directory, do not add another.
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[e2e]" --prerelease=allow`
- Run Python tests in the foreground: `pytest tests/`. `tests/test_smoke.py` is
  fast (import, version, construction, no socket/connect). `tests/e2e/` boots a
  real `hivemind-core` master in-process via hivescope and drives the real
  `WebchatBridge` over a real `HiveMessageBusClient`; only the browser/websocket
  frontend is mocked.
- JS e2e: `npm install && npm test` (runs `tests/v3_negotiation.test.mjs` and
  `tests/e2e.mjs`). The JS e2e loads the exact HiveMind-js client the page
  ships and drives a full V1 handshake against a real loopback hub spawned via
  `tests/hub_fixture.py` — this needs a Python interpreter with the `[e2e]`
  stack on `PATH` (`PYTHON=...` overrides it). No `importorskip`/`skipif`
  guards anywhere; the `[e2e]` stack is a hard dependency for the full suite.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is a
  bug to FIX at the source, not to work around with a pin downgrade.
- See `docs/` for more: [architecture](docs/architecture.md),
  [dependencies](docs/dependencies.md), [testing](docs/testing.md),
  [deployment](docs/deployment.md), [troubleshooting](docs/troubleshooting.md).

## Working agreement (org-wide law)

- **Git identity is always** `JarbasAi <jarbasai@mailfence.com>`. Never set a
  per-repo override.
- **Never push `dev` or `master`.** Work on a feature branch and open a
  **draft** PR into `dev`. A human merges. You do not merge your own PRs.
- **Never merge or modify `Release X → master` PRs.** They are the maintainer's

- **One commit per PR** (squash before pushing). Conventional commits; `feat:`
  only for a user-visible new capability. `fix:`, `docs:`, `chore:`, `ci:`

  Verify before acting.` PR bodies are plain human prose (3–6 short paragraphs),
  no tables or section-symbol spray.

  instead; on your own PRs, edit the body rather than piling on comments.

  no dates, no "currently/now/new", no meta-commentary about the edit itself.
- No scratch files, committed virtualenvs, `__pycache__`, `.pyc`, `.egg-info`,
  or build artifacts in a PR. `git show --stat` shows only intended files.

## Dependencies

- **Floor pins only** (`>=X.Y.Za1`), bumped when a feature or fix is actually
  needed — with a one-line comment saying why. No upper caps unless a specific
  released version is genuinely broken (say which and why). This repo already
  follows the pattern: the `[e2e]` extra restates transitive pre-release floors
  so the HiveMind 2.x stack resolves without `--pre` (see the comments in
  `pyproject.toml`).
- **No lockfiles, ever.** Target the latest alphas (`--prerelease=allow`).
- Everything in `pyproject.toml` (deps, metadata, version). Never install from
  git — depend on a published PyPI alpha. `package.json` covers only the JS
  dev/test tooling (`ws`), not a runtime dependency — the page loads
  HiveMind-js from a CDN, not from npm.
- Apache-2.0. Do not add GPL/AGPL dependencies.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test
  that only asserts a mock was called, without asserting the real behaviour, is
  weak — note it.
- Never skip a test because an optional dependency is missing.
- CI green is permission to review, not to merge. A non-trivial change gets an
  adversarial review before it lands.

## Repo-specific rules

- This is a satellite/app on top of the HiveMind-js client library, not the
  wire protocol itself: the browser negotiates the highest HiveMind protocol
  version both peers support (protocol v3 Noise handshake, `Noise_XXpsk2_25519_ChaChaPoly_SHA256`,
  falling back to the legacy v1 password handshake, PBKDF2-HMAC-SHA256 + AES-GCM,
  against older `hivemind-core`). Do not weaken or bypass that negotiation for
  convenience.
- A named session implies a remote client — do not assume the browser and the
  hub share a machine or a filesystem.
- Bad credentials must fail fast, not hang or silently retry; if you touch the
  connection form or the headless bridge's handshake path, verify the failure
  is surfaced to the user/caller rather than swallowed.
- Never hardcode secrets (access keys, passwords) in source, tests, or docs;
  the quickstart in `README.md` and `docs/getting-started.md` must stay true to
  the real `hivemind-core add-client` / `hivemind-webchat --port` flow — verify
  any doc change against an actual run, don't just edit prose.
- The Python backend only serves the static page and (optionally) runs the
  headless bridge; it never itself terminates the HiveMind connection except
  through `WebchatBridge` — keep that separation when adding backend features.
